# Continuum Prompt 40: WCB engine database (migration and seed)

This directory holds the schema migration and the generated seed SQL for the WCB
Worker 36 form engine (spec `docs/superpowers/specs/2026-08-09-prompt-40-wcb-form-engine-design.md`).

Per the standing rule, Claude never applies anything to the Continuum Supabase
project (`agzhnmunodrhsjbogzae`) directly. Gary applies these files by hand, in
order, via the Management API or the SQL editor.

## Apply order

1. **`001_migration_wcb_engine.sql`** creates the `clinical` schema and all ten
   tables plus the `optionality` enum (spec Sections 2 and 2A). Idempotent, one
   transaction, safe to re-run.
2. **`002_seed_reference_and_lookups.sql`** loads the reference and lookup data.
   Apply after the migration. One transaction, `on conflict do nothing`, safe to
   re-run. GENERATED by `seedgen.mjs`, do not hand edit.
3. **`003_seed_form_elements.sql`** loads all 804 form elements across the eight
   forms. Apply after `002` (needs `form_definition`). One transaction, `on
   conflict do nothing`. GENERATED by `formelementgen.mjs`, do not hand edit.
4. **`004_seed_form_rules.sql`** loads the show/hide, conditional, and
   code_list_switch rules. Apply after `003`. One transaction, `on conflict do
   nothing`. GENERATED by `formrulegen.mjs` from the human reviewed source
   `form_rules.data.mjs`, do not hand edit the SQL (edit the source and
   regenerate). Covers all eight forms in full (C050E, C050S, C151, C151S, and
   the four invoice forms C568, C568A, C569, C570).
5. **`005_migration_capability_code_set.sql`** creates
   `clinical.wcb_capability_code_set`, the per (form, capability element) Basic
   versus Extended table (Prompt 39A Section 2.3). Apply after `001`.
6. **`006_seed_capability_code_set.sql`** loads that table (58 rows). Apply after
   `005`. GENERATED by `capabilitycodesetgen.mjs` from `capability_code_set.data.mjs`.
7. **`007_migration_error_catalogue.sql`** creates `clinical.wcb_error_catalogue`,
   the board error code catalogue (Prompt 39A Section 5). Apply after `001`.
8. **`008_seed_error_catalogue.sql`** seeds the one real board code the package
   contains (1 row). Apply after `007`. GENERATED by `errorcataloguegen.mjs` from
   `error_catalogue.data.mjs`. The catalogue grows from real rejections.
9. **`009_migration_obx_skeleton.sql`** creates `clinical.wcb_obx_skeleton`, the
   per form OBX skeleton in fixed order (Prompt 39A Section 3.1). Apply after `001`.
10. **`010_seed_obx_skeleton.sql`** loads the skeleton (521 observations across the
    eight forms). Apply after `009`. GENERATED by `obxskeletongen.mjs` from the
    board sample XML files.

    **`016_migration_physician_foundation.sql`** (the physician platform FOUNDATION,
    Prompt 43a gate 1) is numbered 016 but **must be applied HERE, after `010` and
    BEFORE `011`**: it creates the parents `011` preflight gates on (`clinical.clinic`,
    `clinical.practitioner`, `clinical.worker`, `clinical.wcb_case`, `clinical.wcb_report`
    with `signed_at` and `snapshot_hash`, `clinical.wcb_submission`, `clinical.consent`,
    `clinical.measurement_draft`, `clinical.clinic_batch_schedule`) plus the append only
    `audit` schema. `case_ref`/`worker_ref` in the employer schema stay opaque, never a
    cross schema foreign key to these. Lives in the dedicated Canada region (Montreal)
    project (Gary creates it and records the region as the prerequisite 7 evidence).
    Idempotent, one transaction.
11. **`011_migration_functional_measurement_model.sql`** (Prompt 39, a SEPARATE
    prompt from the Prompt 40 engine above) creates the physician functional
    measurement model: the `functional_measurement` spine, the axis and detail
    tables (`functional_axis_value`, `functional_grasping`, `functional_reaching`,
    `functional_environment`, `functional_clinical_context`), the internal and
    legacy restriction tables, the append only `band_derivation_audit`, the
    `functional_axis_map` configuration table, and the functions
    `derive_weight_band`, `emit_code` and `resolve_axes` plus the `axis_emitted_only`
    no leak view. It has a PREFLIGHT gate that REFUSES to run until the physician
    platform foundation exists (`clinic`, `wcb_case`, `wcb_report`, `practitioner`),
    so on 2026-08-10 it will abort until those are built. Depends on `form_definition`
    from `001`. Idempotent, one transaction.
12. **`012_seed_functional_measurement.sql`** loads the eight internal restriction
    codes and the per form axis map (60 rows: 11 for `C050E`, 11 for `C151`, 19 for
    `C050S`, 19 for `C151S`). Apply after `011`. GENERATED by
    `functionalmeasurementgen.mjs` from `functional_measurement.data.mjs`, which hard
    gates the axis map against the Section 4.4 board matrix (criteria 2 and 3).
13. **`013_migration_hl7_wire_map.sql`** (Prompt 42) creates
    `clinical.wcb_hl7_wire_map`, the per (form, element) HL7 v2.3.1 placement (segment,
    field position, and the OBX.3 identifier for OBX encoded elements). This is what
    Prompt 40 did not load: `form_element.hl7_xpath` carries only the canonical New XPath
    (`/InjuryReport/...`), which is not the board wire format. Apply after `001`.
14. **`014_seed_hl7_wire_map.sql`** loads that table (678 rows across the eight forms).
    Apply after `013`. GENERATED by `hl7wiremapgen.mjs` from the accreditation workbook
    columns Seg, Seq# and XML Element Representation. The generator also emits
    `hl7_samples.data.mjs` (the OBX skeletons extracted from the `5.xx` samples, used by
    the generator round trip tests) and hard gates that each form's Min OBX skeleton is a
    subset of its Max, the difference being the conditionally available observations
    (Section 2.2, criterion 4).
15. **`015_migration_employer_view.sql`** (Prompt 43) creates the SEPARATE `employer`
    schema with `published_restriction_set` and `duty_match_line`. This is the wall
    between the clinical record and the employer: there is no column here capable of
    holding clinical content, `case_ref` and `worker_ref` are opaque uuids (NOT cross
    schema foreign keys to `clinical`), and a build failing schema test
    (`clinical/engine/employer_schema.test.mjs`, criterion 1) rejects any banned or raw
    measurement column. It has no dependency on `001`; it is a standalone schema. Apply
    any time. Idempotent, one transaction.

## Regenerating the seed

```
cd clinical/db
npm install                       # installs xlsx (build tool only, gitignored)
node seedgen.mjs "<path to 3 - WCB Report Element to HL7 Element Mapping.xlsx>"          # -> 002
node formelementgen.mjs "<path to the same workbook>"                                    # -> 003
node formrulegen.mjs                                                                     # -> 004 (reads form_rules.data.mjs, no workbook)
node capabilitycodesetgen.mjs                                                            # -> 006 (reads capability_code_set.data.mjs, no workbook)
node errorcataloguegen.mjs                                                               # -> 008 (reads error_catalogue.data.mjs, no workbook)
node obxskeletongen.mjs "<dir with the 5.xx sample XML files>"                           # -> 010 (and obx_skeleton.data.mjs)
```

Both generators print an audit. `seedgen` reports per-list value counts and the
criterion 2/3/4 totals and names anything it declines to flatten. `formelementgen`
reports the per-form count gate (writes nothing and exits non zero on any
mismatch), the deprecated and code-list-linked totals, and any unresolved code
list reference or unparseable cell.

### One flagged open item from the form_element parse (spec open item 9.2)

`C570` seq `32.12` references `[See Location Codes]`, but no `Location Codes`
worksheet exists among the 43. The generator stores `Location Codes` verbatim in
`code_list_name` and flags it rather than silently swapping in `Facility Types`.
Resolution is Gary's and Hannah's call, per spec open item 9.2. Similarly `C568A`
seq `34` carries a stray `s` in Max Occ, defaulted to a single occurrence and
flagged.

## NOT emitted yet (documented, not silently skipped)

- **Two composite lookup worksheets** are not flattened into code lists because
  their first column is not a unique code, so a naive flatten would collide or
  mangle them:
  - `Category Type Expedite Codes` (relational: report type + treatment category
    + treatment type; the data source for VAL-X10/X11, which are not implemented
    in the engine yet).
  - `Form ID To Attachment Codes` (one form to many attachment types; the data
    source for the P3 attachment rule, check 9).
  Each needs a small bespoke target table and loader. Tracked as follow-up.
- **`form_rule` is complete for all eight forms**, the **Basic vs Extended code
  set table is built** (`wcb_capability_code_set`, read by
  `clinical/engine/capability.mjs`), and the **namespaced code enums are built**
  (`clinical/engine/codes.mjs`: a weight LIMITED can never be assigned to a
  capability element, enforced by namespace tag not string, criterion 14). The
  the **PHN gate is built** (`clinical/engine/phn.mjs`: exactly nine digits
  enforced in app code since the schema permits a short PHN, plus a default off
  refuse to guess check digit stage, criterion 8), and the **date defect
  passthrough is built** (`clinical/engine/date_defect.mjs`: a real date the
  validation schema wrongly rejects passes and is logged, a date that never
  existed is blocked regardless, criteria 15 and 16), and the **error catalogue
  is built** (`wcb_error_catalogue` + `clinical/engine/errors.mjs`: a board code
  maps to an element only, an unmapped or low confidence code surfaces raw board
  text to a human), and the **OBX skeleton per form is built**
  (`wcb_obx_skeleton` + `clinical/engine/obx.mjs`: the fixed OBX order read from
  each form's board sample, C050E 98 per criterion 4). All of the Prompt 39A new
  work is now built; only the three board enquiries (B1 check digit, B2 date
  defect, B3 attachment shape) and the two composite lookup sheets remain. See the
  39A reconciliation doc for the full list.

Every `form_rule` row stays `verified_against_sample_xml = false` until it is
asserted against its board `5.xx` sample XML (the transcription docs' definition
of done) and, per the clinical pre-flight rule, Hannah signs off the structured
set before any of it drives a live form. The engine code in `clinical/engine/`
already validates against these tables once they are populated.
