# Continuum Prompt 40: WCB engine database (migration and seed)

This directory holds the schema migration and the generated seed SQL for the WCB
Alberta form engine (spec `docs/superpowers/specs/2026-08-09-prompt-40-wcb-form-engine-design.md`).

Per the standing rule, Claude never applies anything to the Continuum Supabase
project (`agzhnmunodrhsjbogzae`) directly. Gary applies these files by hand, in
order, via the Management API or the SQL editor.

## Apply order

1. **`001_migration_wcb_engine.sql`** creates the `clinical` schema and all ten
   tables plus the `optionality` enum (spec Sections 2 and 2A). Idempotent, one
   transaction, safe to re-run.
2. **`002_seed_reference_and_lookups.sql`** loads the reference and lookup data.
   Apply after the migration. One transaction, `on conflict do nothing`, safe to
   re-run. GENERATED by `seedgen.mjs`, do not hand edit.

## What the seed contains (all faithful mirrors of the accreditation workbook)

| Data | Rows | Verified fact |
|---|---|---|
| `jurisdiction` | 13 | Alberta active, all other provinces/territories inactive |
| `wcb_fee_schedule` | 6 | Alberta GP rates effective 2025-04-01 (spec Section 2) |
| `wcb_code_list` + `wcb_code_value` | 25 lists / 606 values | every simple lookup worksheet, codes read as TEXT (01100 stays 01100), padded codes trimmed, per-row flags in `extra` jsonb |
| `wcb_pob_noi_forbidden` | 380 | acceptance criterion 2 (exactly 380 Alberta rows) |
| `wcb_contract_role` | 14 pairs | acceptance criterion 3 |
| `wcb_contract_role_form` | 66 | acceptance criterion 3 (32 source rows normalised to 66; crossover ancestry in `created_from_form_ids`) |
| `form_definition` | 8 | acceptance criterion 4 (verified element counts 111/171/136/153/61/69/37/66; C569 and C570 permit zero attachments) |

## Regenerating the seed

```
cd clinical/db
npm install                       # installs xlsx (build tool only, gitignored)
node seedgen.mjs "<path to 3 - WCB Report Element to HL7 Element Mapping.xlsx>"
```

The generator prints an audit (per-list value counts and the criterion 2/3/4
totals) and reports anything it declines to flatten.

## NOT emitted yet (documented, not silently skipped)

- **Two composite lookup worksheets** are not flattened into code lists because
  their first column is not a unique code, so a naive flatten would collide or
  mangle them:
  - `Category Type Expedite Codes` (relational: report type + treatment category
    + treatment type; the data source for VAL-X10/X11, which are not implemented
    in the engine yet).
  - `Form ID To Attachment Codes` (one form to many attachment types; the data
    source for the P3 attachment rule, check 9).
  Each needs a small bespoke target table and loader. Tracked as follow-up.
- **`form_element`** (the ~700 element rows across the eight forms). Package
  derivable from the form worksheets (Seq, Element Name, UI Mapping, Data Type,
  Length, Format, Max Occ, Valid Values, Optionality, New XPath, plus section
  marker rows), but it needs a faithful per-form column parse with the four
  loader traps handled (deprecated seq 77/80, the C568 35.06 typo, leading zero
  and padded codes) and must be gated on reproducing the verified element counts
  before it is trusted. That is its own loader increment.
- **`form_rule`** (the show/hide and cross field rules). These load from the
  human-reviewed transcription docs under `docs/superpowers/specs/` (the
  `-rules-transcription` files), not from a machine-readable source. Per the
  clinical pre-flight rule, they go in only after Hannah signs off the structured
  rule set. Not improvised into SQL from memory.

The engine code in `clinical/engine/` already validates against these tables once
they are populated; `form_element` and `form_rule` are the remaining data load
before a form can be driven end to end.
